# P0–P1 前期开发方案

> 📌 状态：**现行计划**
> 目标：先证明“规则可迁移”，再证明“战斗成立”。

---

## P0：Portable Core

### P0-A 类型与确定性

最小类型：

```text
EntityId
SimTick
DeterministicRng
RangeMilliGrid
Ratio/FixedValue（如需要）
```

避免一开始建立复杂 Entity framework。

### P0-B Battle DTO

```text
UnitStats
UnitState
BattleConfig
BattleState
GameCommand
SimEvent
BattleSnapshot
BattleResult
```

DTO 必须可用 plain TS interface 近似一对一重写。

### P0-C 最小 Step

建议第一版顺序固定：

```text
ApplyCommands
EvaluateAI/Targeting
AdvanceCooldowns
ResolveAttacks
ResolveDamage/Deaths
EvaluateBattleEnd
AdvanceTick
EmitSnapshot/Events
```

顺序一旦进入 Golden fixture 就属于回放语义；修改需要版本说明。

### P0-D Golden Harness

不要只 assert “winner == Allies”。至少锁：

```text
winner
endTick
remainingHp
shotCount
deathOrder
targetChangeCount
eventHash
finalRngState
```

这样以后重构能分辨“结果一样但过程已漂移”。

### P0-E UE Host

Host 做 fixed-step 驱动、后端组合与 DTO 转换，不另定义玩法。Debug View 的位置可以非常丑。

P0 结束时应存在一种 `-NoVisual`/test path（具体形式按项目事实选择），能证明规则不依赖 View。

### P0-F 可选 Reference Backend

P0/P1 即可使用高级 UE 系统验证已定玩法；遵循 `AGENTS.md` 6.1/G6，不另设系统禁用审批。先写项目 Contract 和同一 scenario，再实现 UE Adapter 或 Portable 子集；允许参考实验先行，规则卡完成前补齐 Portable 与双后端对照。

每次引入记录问题、最小能力、Cocos 等价能力、成本/范围、不迁移内容和退出条件。Host 为每次运行选择一个权威后端，对照后端运行于隔离状态，不合并两套伤害或事件。Core 不依赖 UE，规范 DTO 不含 UE 句柄。

## P1：Battle Sandbox

### P1-A Range Axis

上游已有“格 = 射程公共刻度”的设计。P1 继续使用 1D 主轴：

```text
0 ... 4 grid
```

可额外有 lane/formation offset 供表现，但不先做二维寻路。

必须测试：

- 目标超射程会 approach；
- 进入射程会 engage；
- 太近时可 reposition（若 profile 要求）；
- 死亡目标会重新选择；
- 相同输入 target sequence 稳定。

### P1-B AI

用组合而非继承树：

```text
AiProfile
  preferredRange
  retreatThreshold
  targetPolicy
  aggression
  abilities...
```

Evaluator：

```text
if dead -> dead
if flee condition -> flee
if no target -> acquire
if too far -> approach
if too near -> reposition
else -> engage
```

P1 先追求可解释与确定性，再追求“聪明”。

可先用 StateTree/BT 探索上述状态转换，用 EQS 验证候选生成/过滤/评分，但输入输出仍为相同 AiProfile/AiIntent 契约。同分排序、状态生命周期、fixed tick 与随机调用顺序必须可复现，并由 Portable evaluator 对照。

### P1-C Ballistic Semantic

先实现至少三种：

1. direct；
2. pierce 或 multishot；
3. blast。

目的不是内容量，而是证明：同一 Rule Semantic 可以被 UE 多种视觉轨迹表现。

View 端建议先：

```text
Debug line
简单 sprite proxy
Niagara（P0/P1 即可作为表现 Adapter；P2 专门验证弹道读感）
```

### P1-D Energy/Heat

规则层只建一个共享能量语义与单位热量/过热事实；UI 是否漂亮不影响 P1。

检查：

- 能量只有一个权威值；
- 技能消费可复现；
- 过热改变攻击能力但不依赖材质/动画通知。

技能/效果可通过项目 AbilityRequest/EffectSpec facade 接 GAS 参考后端；成本、冷却、目标合法性与效果顺序由中立 Contract 定义，GAS 对象不进入规范状态。

### P1-E Choice

三选一必须建成明确状态/命令：

```text
ChoiceOffered
ChoiceOption[3]
ChooseOptionCommand
ChoiceApplied
```

战斗 simulation 不暂停；玩家尚未选择时继续推进。

如果需要超时自动选，超时使用 sim time，不读真实 wall clock。

### P1-F Battle Lab

Battle Lab 是原型最重要的开发面，不是正式 UI。

最低功能：

- 选择/输入 seed；
- 重开；
- 单步 simulation；
- host pause；
- 1x/2x/5x/10x；
- 选择 ally/enemy fixture；
- 显示当前 tick、单位状态、目标；
- 导出/复制 Golden result。

Battle Lab 不拥有另一套 battle 逻辑。

## P1 完成验收

P1 通过需要同时满足：

### 规则面

- 2 起始角色到最多 5 人的 fixture 可跑；
- N 敌人自动战斗可收束；
- AI、射程、攻击、弹道语义、能量/热量、Choice 有自动测试；
- 同 seed 可复现。

### 架构面

- Core Boundary 仍全绿；
- Core 无 UE types；
- Actor 无权威 HP/AI；
- 不依赖碰撞通知完成命中；
- 数据/状态可表达成未来 TS plain interfaces。
- 采用 UE 规则参考后端的系统通过 G6；未采用者不强制开发第二套后端。

### 表现面

- 玩家能看到阵营；
- 能看出当前目标；
- 能看出接近/交战/后退；
- 至少三种 ballistic semantic 在视觉上可区分；
- 三选一上屏但战斗不停。

### 迁移门

**P1 后立即进入 P1.5，不允许先继续堆 P2 表现。**

这是阶段验收顺序，不限制在 P0/P1 使用 Niagara、UMG、动画等表现工具。

## P1.5：迁移演习

只迁一小块，不迁全游戏：

```text
DeterministicRng
Target selection
一段 Battle Step / damage resolution
Scenario fixture
```

TS 版本不得 import Cocos。

对齐：

```text
C++ result.json
TS result.json
```

至少比较：

```text
winner
endTick
remainingHp
shotCount
deathOrder
targetChangeCount
rngState
```

若难以机械重写，优先重构 C++ Core，而不是在 TS 写适配垃圾。

这里机械重写的对象仅为项目独立编写的 Portable C++。UE Engine Code 不复制、不逐行翻译；从研究中提炼最小契约后独立实现。若代表切片采用 UE Reference Backend，同时保留其 G6 对照证据；不能以 UE/C++ 对照替代 C++/TS 对照。

## 前期明确不做

- 完整母舰 UI；
- 全部 20–25 层内容；
- 最终数值平衡；
- 完整角色成长；
- 完整 7+ 敌族内容；
- 大层 2×2 AI 寻路；
- 商业化；
- 最终存档兼容政策；
- 为最终品质制作完整的高端动画资产体系（可使用 UE 动画工具验证表现）；
- 无实际规模或性能证据的 Mass/ECS 全量移植或存储重构（允许隔离研究与小范围实验）。

只有测到真实性能瓶颈后才引入复杂优化。
